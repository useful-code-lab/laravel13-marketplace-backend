# 🛒 Laravel 13 Marketplace Backend — DDD, CQRS, API и надёжная обработка заказов

Практическое backend-ядро мультивендорного маркетплейса на **Laravel 13**, созданное как пример построения масштабируемого API с чётким разделением бизнес-логики, безопасной обработкой заказов и удобной административной панелью.

Проект будет полезен разработчикам, которые хотят не просто посмотреть пример CRUD на Laravel, а разобраться, **как организовать архитектуру реального коммерческого приложения**: разделить бизнес-домены, защититься от конкурентных изменений остатков, вынести тяжёлые операции в очереди, организовать кэширование и изолировать внешние платёжные сервисы.

## 🎯 Что можно получить из проекта

Репозиторий можно использовать как готовый учебный и практический пример при разработке собственных Laravel-приложений.

### Если вы изучаете Laravel и архитектуру

Вы сможете увидеть на реальном проекте:

* как организовать код по принципам **Domain-Driven Design (DDD)**;
* как отделить HTTP-слой от бизнес-логики;
* как использовать **DTO** вместо передачи неструктурированных массивов;
* как применять **CQRS** для разделения операций чтения и изменения данных;
* как организовать взаимодействие компонентов через доменные события;
* как строить код так, чтобы отдельные части приложения было проще тестировать и изменять.

### Если вы разрабатываете API

Проект показывает практический сценарий построения REST API для маркетплейса:

* регистрация пользователей и авторизация через Laravel Sanctum;
* разделение ролей `customer` и `vendor`;
* управление товарами;
* создание заказов;
* обработка платежей через отдельный контракт;
* webhook для получения информации об оплате;
* пагинация каталога;
* кэширование результатов запросов.

### Если вас интересует надёжность backend-систем

Особенно полезна реализация оформления заказа.

При покупке нескольких товаров приложение должно одновременно проверить и изменить остатки. Для предотвращения проблем при параллельных запросах используется **транзакция базы данных и `lockForUpdate`**.

Это позволяет изучить на практическом примере, как защищать критические операции от race condition.

### Если вы хотите масштабировать бизнес-логику

Побочные операции не смешиваются непосредственно с оформлением заказа.

После создания заказа генерируется доменное событие `OrderCreated`, после чего связанные тяжёлые процессы могут выполняться асинхронно через очереди.

Такой подход позволяет отделить основную бизнес-операцию от уведомлений, интеграций и других фоновых задач.

### Если нужно заменить платёжную систему

Платёжная инфраструктура скрыта за `PaymentGatewayInterface`.

Бизнес-логика работает не с конкретным платёжным сервисом, а с контрактом. Поэтому реализацию платёжного шлюза можно заменить без переписывания основной логики заказов.

Например, это позволяет использовать разные интеграции с платёжными провайдерами в зависимости от конфигурации приложения.

## 🧩 Архитектура проекта

Основная бизнес-логика разделена по доменам внутри `src/Domain/`.

```text
src/
└── Domain/
    ├── Products/
    │   ├── Models/
    │   ├── Data/
    │   ├── Queries/
    │   └── ...
    │
    └── Orders/
        ├── Models/
        ├── Data/
        ├── Events/
        ├── Services/
        └── ...
```

HTTP-часть приложения располагается отдельно в `app/`.

Такое разделение помогает не превращать контроллеры и Eloquent-модели в единое место для всей бизнес-логики.

## 🏗️ Основные архитектурные решения

### Domain-Driven Design

Предметная область разделена на отдельные бизнес-домены:

* `Products`;
* `Orders`.

Это позволяет развивать отдельные части системы независимо и уменьшает связанность компонентов.

### DTO

Для передачи данных используются типизированные объекты:

* `ProductData`;
* `OrderData`.

Вместо неструктурированных массивов бизнес-логика получает объекты с определённой структурой и типами данных.

### CQRS

Получение каталога вынесено в отдельные Query-классы.

Это позволяет независимо оптимизировать операции чтения и изменения данных, а также централизовать логику получения каталога.

### Кэширование каталога

Каталог поддерживает кэширование результатов запросов.

При изменении товаров соответствующий кэш инвалидируется, благодаря чему пользователю не приходится постоянно обращаться к базе данных за одними и теми же данными.

### Транзакции и блокировки

Оформление заказа выполняется внутри транзакции.

Для изменения остатков используется:

```php
lockForUpdate()
```

Это демонстрирует практический способ защиты складских остатков при одновременном оформлении заказов несколькими пользователями.

### Event-Driven Architecture

Создание заказа сопровождается событием:

```text
OrderCreated
```

События позволяют отделить основную операцию от дополнительных процессов и передавать тяжёлые задачи в очереди.

### Strategy и Dependency Inversion

Платёжный шлюз определяется через:

```php
PaymentGatewayInterface
```

Бизнес-логика не зависит напрямую от конкретного платёжного провайдера.

### RBAC

Доступ к операциям API ограничивается ролями пользователей:

```text
customer
vendor
```

Для проверки разрешений используются Laravel Policies.

В проект интегрирован **Filament**, который предоставляет отдельный интерфейс для управления приложением.

## 🔌 REST API

### Авторизация

```http
POST /api/auth/register
```

Регистрация пользователя с ролью:

```text
customer
vendor
```

После регистрации API возвращает Bearer-токен.

### Каталог

```http
GET /api/products
```

Получение каталога товаров с пагинацией и кэшированием.

Для создания товара:

```http
POST /api/products
```

Операция доступна авторизованному пользователю с ролью `vendor`.

### Заказы

```http
POST /api/orders
```

Создание заказа.

В процессе обработки:

1. проверяются товары;
2. проверяется доступный остаток;
3. рассчитывается стоимость;
4. остатки изменяются внутри транзакции;
5. создаётся заказ;
6. запускается дальнейшая обработка платежа.

### Webhook платежа

```http
POST /api/webhooks/payment
```

Используется для получения уведомления от платёжной системы.

Webhook защищён подписью:

```text
X-Payment-Signature
```

и поддерживает защиту от повторной обработки одного и того же события.
